# ipguard: 쿼리 트리 수준에서 집행하고 판정 불가 시 거부하는 PostgreSQL 동적 PII 마스킹

**저자:** 오병훈 (중앙대학교 융합보안학과)

> 연구 프로토타입에 대한 기술 보고서. 본문의 모든 정량 수치는 합성 코퍼스와 TPC-H 기준이며, 우수성·유일성 주장은 "본 연구가 비교한 기법 가운데"로 한정한다. 본 연구의 안전성 논증은 설계 수준(design-level)이며 형식 검증(formal verification)이 아니다.

---

## 초록 (Abstract)

관계형 데이터베이스의 **동적 데이터 마스킹(dynamic data masking)**은 민감정보(PII)를 저장은 그대로 두되 질의 결과에서만 가려 보여주는 기법이다. 그러나 결과 바이트를 사후에 가리는 방식(출력단 마스킹)은 `length(ssn)`, `substr(ssn,1,6)` 같은 **한 줄짜리 표현식**으로 우회된다. 공격자(또는 과도한 권한을 가진 애플리케이션 역할)는 가려진 컬럼을 표현식으로 감싸, 원본의 길이·앞자리·존재 여부 같은 정보를 그대로 빼낼 수 있다. 출력 스트림의 `resorigtbl/resorigcol`만 검사하는 와이어 레벨 탐지기로 이 노출을 재현하면 55건의 노출 중 21건(38%)만 탐지된다.

본 연구는 **ipguard**를 제안한다. ipguard는 PostgreSQL 확장으로서, 질의가 계획(planning)되기 전 `planner_hook`에서 쿼리 트리의 PII `Var`를 base 컬럼까지 해석하여 마스킹 함수 `ipguard_mask()`로 치환한다. 따라서 표현식은 이미 마스킹된 값 위에서 계산되고, 출력단 우회가 **구조적으로** 성립하지 않는다. 또한 ipguard는 동적 마스킹의 설계 공간을 **충실도(Fidelity)·불투명성(Opacity)·완전성(Totality)**의 삼자택이로 보고, 안전하게 마스킹할 수 있는지 판정할 수 없는 질의를 열화(degrade)가 아니라 **거부(fail-closed)**하는 세 번째 꼭짓점을 택한다. 합성 코퍼스에서 AST 탐지 회수율 95%, 마스킹 집행 92%(과마스킹 0), release-factorization 게이트의 경계 폐쇄성 118/118을 얻었으며, TPC-H 22개 질의에 대한 기본 거부율은 0/22(판정식 활성화 시 5/22)였다.

## 1. 서론

데이터 보호 규제와 내부 통제가 강화되면서, 운영 DB에서 PII를 저장 단계가 아니라 **질의 응답 단계에서 가리는** 동적 마스킹이 널리 쓰인다. 애플리케이션 코드를 바꾸지 않고도 특정 역할에게 가려진 값을 돌려줄 수 있다는 점이 매력이다.

문제는 **마스킹을 "어디서" 집행하느냐**에 있다. 많은 구현은 결과가 거의 완성된 뒤, 출력 바이트를 치환한다. 이 방식에서 마스킹은 파이프라인의 **맨 끝**에 놓인다. 그런데 공격자가 원본을 직접 요구할 필요가 없다. 가려진 컬럼을 표현식으로 **감싸기만** 하면 된다.

```sql
-- 가려진 ssn 컬럼이라도:
SELECT substr(ssn, 1, 6) FROM customers;   -- 생년월일 앞 6자리 노출
SELECT length(ssn) FROM customers;         -- 원본 길이 노출
SELECT ssn LIKE '8810%' FROM customers;    -- 존재 여부로 값 추측
```

`substr`·`length`는 **원본** `ssn` 위에서 먼저 계산되고, 마스킹은 그 뒤에 적용되거나 애초에 표현식 결과에는 적용되지 않는다. 즉 **연산 순서**가 뒤집혀 있다. 이 노출을 출력 스트림 기준으로만 탐지(`resorigtbl/resorigcol` 검사)하면 55건 중 21건(38%)만 걸린다 — 표현식으로 감싼 노출의 다수가 와이어에서 base 컬럼으로 역추적되지 않기 때문이다.

본 논문의 기여는 다음과 같다.

1. **집행 지점의 재배치.** 출력 바이트가 아니라, 계획 전의 **쿼리 트리**에서 PII `Var`를 마스킹 함수로 치환한다. 표현식은 가려진 값 위에서 계산되므로 우회 지점이 사라진다.
2. **삼자택이(trilemma) 관점.** 동적 마스킹을 충실도·불투명성·완전성의 긴장으로 정식화하고, 판정 불가 질의를 거부(fail-closed)하는 설계를 택한다.
3. **release-factorization 게이트.** 원본에 대한 비교가 "공개된 정보(release)"로부터 재구성 가능한지를 판정하고, 불가하면 질의를 거부한다.
4. **적대적 자기검증.** 집행 경로 자체의 결함(예: 제어용 GUC가 전부 사용자 설정 가능 → 마스킹을 한 줄로 끌 수 있음)을 스스로 찾아 고쳤다.

## 2. 배경과 위협 모델

### 2.1 동적 데이터 마스킹과 집행 지점

질의 처리는 대략 **파서 → 재작성(rewrite) → 계획(planner) → 실행(executor) → 출력**의 단계를 거친다. 마스킹을 어느 단계에 넣느냐에 따라 보호의 성질이 달라진다.

- **출력단(와이어) 마스킹:** 결과 바이트를 사후 치환. 구현이 단순하지만, 표현식이 원본 위에서 먼저 계산되므로 우회된다.
- **트리 수준 마스킹(본 연구):** 계획 전에 트리의 PII `Var`를 마스킹 함수로 치환. 이후의 모든 연산은 가려진 값을 입력으로 받는다.

### 2.2 위협 모델

- **방어 대상:** 저장된 PII의 원본 값 및 그로부터 재구성 가능한 파생 정보(길이·앞자리·존재 여부 등).
- **공격자:** 마스킹이 적용되는 역할로 **임의의 읽기 질의를 실행할 수 있는** 주체. 정상 애플리케이션 역할이 과도한 권한을 가진 경우, 혹은 그 역할을 통한 SQL 인젝션을 포함한다.
- **공격 수단:** 가려진 컬럼을 표현식·서브쿼리·CTE·조인 술어로 감싸 원본 정보를 간접 노출.
- **가정 밖:** 저장 계층 직접 접근, 슈퍼유저, OS 수준 접근, 부채널(타이밍) 공격은 본 범위 밖이다.

## 3. 설계 공간: 충실도·불투명성·완전성 삼자택이

동적 마스킹은 세 가지를 동시에 완벽히 만족할 수 없다.

- **충실도(Fidelity):** 가리지 않아도 되는 값은 정확히 보존한다(분석 유용성).
- **불투명성(Opacity):** 가려야 하는 값과 그 파생 정보는 새지 않는다(보호).
- **완전성(Totality):** 모든 질의에 대해 항상 결과를 돌려준다(가용성).

출력단 마스킹은 완전성과 충실도를 택하고 **불투명성을 희생**한다(표현식 우회). 반대로 안전을 위해 애매한 질의마다 거짓/열화된 값을 내보내면 **충실도가 조용히 깨진다**(사용자는 틀린 값을 참으로 오인).

ipguard는 **불투명성을 우선**하고, 안전하게 가릴 수 있는지 판정할 수 없을 때 완전성을 포기한다 — 즉 **열화 대신 거부(fail-closed)**한다. 애매하면 틀린 값을 흘리느니 질의를 막는다.

## 4. ipguard 설계

ipguard는 세 단계로 동작한다: **탐지(detect) → 집행(enforce) → 거부(reject)**.

### 4.1 탐지 — Var의 base 컬럼 해석

파싱·재작성이 끝난 `Query` 트리를 순회하며 모든 `Var`를 **base 컬럼까지** 해석한다. 표현식·서브쿼리·CTE·조인을 관통하여, 중간 별칭·파생 컬럼이 결국 어떤 실제 테이블 컬럼에서 왔는지를 역추적한다. 이때:

- **출력 컬럼 참조**(SELECT 리스트)와
- **술어 참조**(WHERE/JOIN/HAVING 등, 결과에 직접 나타나지 않지만 값을 추론하게 하는 **부채널**)

를 분리해 보고한다. 부채널 참조를 따로 다루는 이유는, 출력에 없더라도 `WHERE ssn LIKE '8810%'` 같은 술어가 원본에 대한 정보를 흘릴 수 있기 때문이다.

### 4.2 집행 — planner_hook에서의 치환

`planner_hook`에서, 식별된 PII `Var`를 마스킹 호출 `ipguard_mask(var, kind)`로 치환한 뒤 표준 플래너에 넘긴다. 치환이 **계획 전**에 일어나므로, 그 위에 쌓인 모든 표현식(`substr`, `length`, 비교 등)은 가려진 값을 입력으로 받는다. 보호할 컬럼 목록은 라벨 테이블(`ipguard_watch_labels`)로 관리한다.

### 4.3 거부 — release-factorization 게이트

술어가 원본에 대한 비교를 포함할 때, 그 비교가 **이미 공개된 정보(release)로부터 재구성 가능한지**를 판정한다.

- 재구성 가능하면(추가 정보를 흘리지 않으면) → **허용**.
- 재구성 가능 여부를 **판정할 수 없으면** → `unknown → reject`. 즉 안전을 증명하지 못한 질의는 거부한다.

이 게이트가 삼자택이에서 완전성을 포기하는 지점이다. 열화된 값을 조용히 내보내는 대신, 보호를 보장할 수 없는 질의를 명시적으로 막는다.

## 5. 구현

ipguard는 PostgreSQL 16용 **C 확장**으로 구현된다.

- **훅:** `planner_hook`을 설치해 계획 직전 트리를 변형한다.
- **마스킹 함수:** `ipguard_mask(value, kind)` — 종류(kind)별 마스킹 정책 적용.
- **질의 단위 판정 API:** `ipguard_verdict(query)` / `ipguard_explain(query)` — 특정 질의가 허용/거부되는지와 그 이유를 노출.
- **라벨 관리:** `ipguard_watch_labels('h5.pii_label')`로 보호 대상 컬럼을 등록.

```sql
CREATE EXTENSION ipguard;
ALTER ROLE app_role SET ipguard.enforce = on;   -- 세션이 아니라 롤/전역 기본값으로 켠다
GRANT SELECT ON h5.pii_label TO app_role;
SELECT ipguard_watch_labels('h5.pii_label');
```

### 5.1 집행 경로의 적대적 자기검증

집행 메커니즘 자체를 공격 대상으로 두고 점검한 결과, 다음 결함을 발견해 수정했다.

- **제어용 GUC의 권한 등급 오류.** ipguard의 제어 GUC 6개가 모두 `PGC_USERSET`으로 선언되어 있었다. 이 경우 애플리케이션 역할이(또는 그 역할을 통한 SQL 인젝션이) `SET ipguard.enforce = off` **한 줄**로 마스킹을 끌 수 있다. 즉 집행기 자체가 자신이 막으려던 공격 표면(임의 질의 실행)으로 무력화되었다. 이를 `PGC_SUSET`으로 전환하여, 상위 권한 없이는 집행을 끌 수 없게 했다.

이 사례는 "마스킹 규칙"뿐 아니라 **마스킹을 켜고 끄는 제어면(control plane)** 역시 위협 모델에 포함되어야 함을 보여준다.

## 6. 평가

### 6.1 정량 결과

합성 코퍼스와 TPC-H를 대상으로 측정했다.

| 측정 항목 | 결과 |
|---|---|
| 와이어(출력단) 기준선 탐지 | 38% (55건 중 21건) |
| AST(트리) 탐지 회수율 | 95% |
| 마스킹 집행 | 92%, 과마스킹 0 |
| release-factorization 게이트 경계 폐쇄성 | 118/118 |
| 거부율 (TPC-H 22개 질의) | 0/22 (판정식 on: 5/22) |

**해석.**
- 출력단 기준선은 표현식 우회 노출의 다수를 놓친다(38%). 트리 수준 탐지는 base 컬럼까지 역추적하므로 회수율이 95%로 올라간다.
- 마스킹 집행은 식별된 PII의 92%에 적용되었고, 가리지 않아도 되는 값을 과도하게 가리는 **과마스킹은 0건**이었다.
- release-factorization 게이트는 구성한 **경계 사례 118개 전부에서 일관되게 닫혔다(폐쇄성 유지)**.
- 정상 분석 질의(TPC-H 22개)는 기본 설정에서 **전부 통과(거부 0)**했다. 즉 거부 정책이 일반 분석을 과도하게 막지 않는다. 판정식을 활성화하면 5개가 거부되는데, 이는 보호-유용성 트레이드오프를 켜고 끌 수 있음을 보인다.

> 평가 기준 주의: 위 수치는 합성 코퍼스 및 TPC-H에 대한 것이다. 성능(지연·처리량)은 공유 서버 환경 제약으로 측정하지 못했다. 우수성 주장은 비교한 기법 가운데로 한정한다.

### 6.2 교차 검증

기존 도구인 **PostgreSQL Anonymizer**와 대표 질의에 대해 동작을 교차 비교하여, 표현식 우회 시나리오에서의 차이를 확인했다(상세 로그는 저장소 `results/crosscheck-anon.md`).

## 7. 한계 및 향후 과제

본 연구는 **연구 프로토타입**이며, 다음을 명시한다.

- **성능 미측정.** 공유 서버 환경이라 지연·처리량 오버헤드를 측정하지 못했다.
- **안전성 논증의 성격.** 트리 수준 집행이 "표현식 우회를 구조적으로 막는다"는 주장은 **설계 수준 논증**이며, 기계 검증된 **형식 증명이 아니다**.
- **평가 범위.** 합성 코퍼스와 TPC-H에 한정된다. 실제 운영 워크로드·대규모 스키마에서의 일반화는 검증되지 않았다.
- **미완 항목.** legacy 게이트 재측정, 정리(cleanup) 증명, eBPF/JDBC 수준 에이전트는 미완이다.
- **유일성 주장의 한정.** 본 연구가 비교한 기법 가운데에서의 상대적 결과이며, 모든 동적 마스킹 도구에 대한 우위를 주장하지 않는다.

## 8. 결론

동적 데이터 마스킹의 취약성은 알고리즘이 아니라 **집행 지점**에 있다. 출력 바이트를 사후에 가리면 표현식 한 줄로 우회되지만, 계획 전 쿼리 트리에서 PII `Var`를 마스킹 함수로 치환하면 모든 후속 연산이 가려진 값 위에서 수행되어 우회가 구조적으로 사라진다. ipguard는 여기에 더해, 안전하게 가릴 수 있는지 판정할 수 없는 질의를 열화 대신 거부하는 fail-closed 설계를 택했다. 합성 코퍼스에서 출력단 기준선 대비 탐지·집행을 크게 끌어올렸고, 정상 분석 질의는 기본 설정에서 전부 통과시켰다. 집행기 자체의 제어면을 적대적으로 점검해 결함을 고친 과정은, 마스킹 시스템에서 "규칙"만큼 "제어면"도 위협 모델에 포함되어야 함을 보인다.
