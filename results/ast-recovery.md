# AST 순회 탐지기 회수율 — 실측 (2026-08-08)

**측정 대상:** PostgreSQL C 확장 `ipguard`가 재작성 후 Query 트리를 걸어
`Var`를 base relation 컬럼까지 해석할 때, 와이어 기준선 대비 얼마를 회수하는가.

**환경:** db.example.internal, PostgreSQL 16.10 소스 빌드, 동일 코퍼스 72항목.
원시 출력: [`ast-recovery.txt`](ast-recovery.txt) / 기준선: [`wire-baseline.md`](wire-baseline.md)

## 남은 미탐 3건 — 원인이 하나다

| ID | SQL | 왜 |
|---|---|---|
| F01 | `SELECT f_ssn(id) FROM cust` | SQL 함수 본문(`SELECT ssn FROM cust WHERE id=$1`)이 호출부 트리에 없다. FROM 절이 있는 SQL 함수는 `inline_function` 대상이 아니라 계획해도 전개되지 않는다 |
| F02 | `SELECT * FROM f_srf()` | `RTE_FUNCTION`. 반환 타입은 알지만 본문은 모른다 |
| F03 | `SELECT f_dyn('ssn')` | plpgsql `EXECUTE format(...)`. 계획 시점에 알 수 있는 것이 없다 |

**셋 다 "함수 본문은 호출부 계획에 존재하지 않는다"는 단일 원인이다.**
계획 트리를 아무리 정교하게 걸어도 **탐지**로는 회수할 수 없다.

> ### ⚠️ 정정 (2026-08-08, `enforcement.md` §1)
> 위 문단은 *"대응은 탐지가 아니라 정책이어야 한다"* 로 끝났었다.
> **탐지에 대해서는 맞지만 집행에 대해서는 틀렸다.**
> `planner_hook` 집행은 F01(UDF 본문)·F03(동적 SQL)·X03(SECURITY DEFINER)을
> **전부 마스킹한다** — 함수 본문도 실행 시점에는 각각 계획을 거치므로
> 훅이 발화하기 때문이다. 실측으로 확인했다.
> 집행에서 남는 것은 F02/T04 뿐이고 원인도 다르다: FROM 절 SRF 를
> 플래너가 **우리 훅 이후에** 인라인하기 때문이다.
> 즉 **집행이 탐지보다 넓다.** 두 지표를 따로 재지 않았으면 몰랐을 것이다.

## 오탐 0 — 부정행위 검사 통과

탐지기가 컬럼명 문자열이 아니라 카탈로그 라벨(`h5.pii_label`)만 근거로
삼는지 실측했다.

| 시나리오 | 결과 |
|---|---|
| 무해한 이름(`alpha`)의 **라벨된** 컬럼을 `substr()`로 감쌈 | **탐지됨** (`out=ssn`) |
| `ssn`이라는 이름의 **라벨 없는** 컬럼 | **탐지 안 됨** (`out=`) |
| 둘을 섞은 쿼리 | 라벨된 것만 탐지 |

`D08`(non-PII 자유텍스트에 주민번호 형태 문자열을 심은 함정)도 통과.
**카탈로그 provenance 기반은 과마스킹하지 않는다**는 성질이 AST로 넘어와도
유지된다.

## 술어 참조 축은 따로 잰다

부채널 항목(S01–S05, `WHERE ssn LIKE '8001%'`)은 출력에 PII가 없으므로
마스킹으로는 막을 수 없는 별개 클래스다. 탐지기는 `out=` 과 `pred=` 를
분리 보고하며, 술어 참조 56항목 중 **50건(89%)** 을 잡았다.

이 숫자를 마스킹 지표에 합산하면 안 된다. 이것은 **쿼리 형태 정책의 입력**이지
마스킹 성능이 아니다.

## 정책 미결로 남은 2건

`E17 = SELECT length(ssn)`, `E18 = SELECT ssn IS NOT NULL`.

탐지기는 `ssn` 참조를 정확히 본다. 와이어는 `length()`를 뚫지 못해 "통과"
했을 뿐 맞는 이유로 통과한 것이 아니다. **노출로 셀지는 집행 지점에 달렸다:**

- **소스 컬럼 마스킹**(표현식 평가 *전*에 Var의 값을 치환) → `length(마스크값)`이
  되어 정상 동작. E01 `substr(ssn,1,6)`도 마스크된 값에 대해 계산된다.
- **출력 바이트 마스킹**(DataRow 재작성) → 정수 `13`을 마스킹할 방법이 없다.

**AST 탐지가 열어주는 것은 전자다.** 이건 단순한 회수율 개선이 아니라
집행 지점을 바꿀 수 있게 하는 결과이며, 다음 설계 결정의 입력이다.
라벨을 바꿔 오탐을 없애지 않고 `derived_only`로 분리 집계했다 —
탐지기에 맞춰 정답을 고치면 측정이 무의미해진다.

## 이 측정이 보여주지 **않는** 것

정직하게 남긴다.

1. **탐지 ≠ 집행.** 마스킹은 구현하지 않았다. 95%는 "어느 컬럼을 가려야
   하는지 안다"는 뜻이지 "가렸다"는 뜻이 아니다.
2. **비용을 재지 않았다.** `ipguard_analyze`는 호출마다 파스+재작성을 새로
   한다. 프로덕션에서는 `planner_hook`에 붙어 이미 수행된 작업을 재사용하므로
   한계 비용은 순회분뿐이지만, **측정하지 않았다.**
3. **탐지기 자체에 대한 적대적 시험이 없다.** 순회기를 미탐시키거나 스택을
   터뜨리는 쿼리를 만들 수 있는지 시험하지 않았다. `MAX_DEPTH`/`MAX_STACK`
   초과 시 `unresolved`로 세지만 그 경로의 fail-closed 처리는 미구현.
4. **바이너리 포맷 경로 미측정.** B01/B05는 분석 단계에서는 통과하지만
   실제 바이너리 전송에서의 마스킹은 별개 문제다.
5. **PG 16에서만 측정했다.** 17/18 이식성 미확인.
