# 집행(마스킹) 검증 — 실측 (2026-08-08)

**집행 방식:** 출력 바이트를 고쳐 쓰지 않는다. `planner_hook` 에서 **계획 전에**
Query 트리의 PII `Var` 를 `ipguard_mask(var, kind)` 호출로 치환한다.

```
substr(ssn,1,6)      ->  substr(mask(ssn),1,6)      ->  "******"
concat(name,'/',ssn) ->  concat(mask(name),'/',...) ->  "***/**************"
length(ssn)          ->  length(mask(ssn))          ->  14
row_to_json(c)       ->  row_to_json(ROW(mask(...)))
```

**표현식 우회가 구조적으로 무력해진다.** 출력 바이트 마스킹으로는 불가능한
성질이며, 이것이 AST 탐지가 열어준 집행 지점이다. `length(ssn)`(E17)이
자연히 해결되는 것도 같은 이유다 — 마스크된 값 위에서 계산되므로.

원시 출력: [`enforcement.txt`](enforcement.txt)

검증 방법: 각 쿼리를 `enforce=off` / `on` 으로 두 번 실행해 결과를 비교한다.
PII 노출 항목은 **달라져야** 하고, 음성 대조군은 **같아야** 한다.
탐지율과 따로 재는 이유는 아래 §2.

## §1 ★ 집행이 탐지보다 넓다 — 이전 결론을 정정한다

`ast-recovery.md` 에서 함수 미탐 3건(F01 UDF / F02 SETOF / F03 동적 SQL)을
*"셋 다 함수 본문이 호출부 계획에 없다는 단일 원인이며 대응은 탐지가 아니라
정책이어야 한다"* 고 썼다. **탐지에 대해서는 맞지만 집행에 대해서는 틀렸다.**

실측:

| | 탐지 | 집행 |
|---|:-:|:-:|
| F01 `f_ssn(id)` UDF 본문 | ✗ | **✅ `**************`** |
| F03 `f_dyn('ssn')` 동적 SQL(`EXECUTE`) | ✗ | **✅** |
| X03 `f_sd(id)` SECURITY DEFINER | ✗ | **✅** |
| F02 `SELECT * FROM f_srf()` | ✗ | ✗ |
| T04 `SELECT * FROM f_inline()` | ✗ | ✗ |

**이유: 함수 본문은 각각 따로 계획되므로 `planner_hook` 이 그 계획에도
발화한다.** 호출부 트리에서 안 보여도 실행 시점에는 반드시 계획을 거치므로
집행은 걸린다. 동적 SQL도 마찬가지 — `EXECUTE` 가 만드는 쿼리도 계획된다.

**F02/T04 만 남는 이유는 다르다.** FROM 절 SRF 는
`inline_set_returning_function` 이 **`standard_planner` 안에서**, 즉 우리 훅이
이미 실행된 *뒤에* 바깥 계획으로 인라인한다. 인라인된 `Var` 는 변이기를
한 번도 통과하지 않는다.

→ 남은 함수 계열 누출은 "함수 본문이 안 보인다"가 아니라 **"플래너가 우리
훅 이후에 인라인한다"** 이다. 대응도 다르다: 훅을 계획 *후*로 옮기거나
(`PlannedStmt` 순회), 집행 세션에서 SRF 인라인을 억제해야 한다.

## §2 탐지와 집행은 반드시 따로 재야 한다

전체 행 `Var`(`row_to_json(c)`)에서 실제로 격차가 있었다. 탐지기는 7종 전부
잡는데 변이기는 `varattno <= 0` 을 건너뛰어 **하나도 안 가렸다.**
"가렸다고 믿는데 안 가려진" 최악의 상태이며, 탐지율만 봤다면 보이지 않는다.

수정: 전체 행 `Var` 를 `expandRTE()` 로 펼쳐 컬럼별 마스킹한 `RowExpr` 로 치환.

| | 결과 |
|---|---|
| `row_to_json(c)` | PII 7종 마스킹, `id`/`grade`/`balance`/`memo` 보존 |
| `to_jsonb(c)` | 동일 |
| `json_agg(t)` (서브쿼리 전체 행) | 마스킹 |

같은 측정에서 **LATERAL 격차**도 잡았다 — `SELECT c.id, l.v FROM cust c,
LATERAL (SELECT c.ssn AS v) l` 은 탐지는 되는데 집행이 안 됐다. 변이기가
`varlevelsup != 0` 을 건너뛰었기 때문. 변이 패스에도 쿼리 스택을 넣어 수정.

## §3 남은 누출 7건 — 전부 기지의 두 클래스

| ID | 클래스 |
|---|---|
| M01·M02 `mv_cust` | **물질화**: 구체화 뷰는 릴레이션이라 사본 컬럼에 라벨이 없다 |
| M03 `ctas_cust` | **물질화**: CTAS 사본 |
| M04·M05 `gen_t.ssn6`, `ssn_rev` | **물질화**: 생성 컬럼 |
| F02·T04 | **플래너 인라인**(§1) |

물질화 클래스는 탐지·집행 모두 원리적으로 불가하다. 대신 **복사되는 순간을
`write` 축이 잡는다**(`INSERT ... SELECT ssn`, `CREATE TABLE AS`, `MERGE`).
대응은 (i) `write` 로 유입 차단 또는 (ii) 라벨 자동 전파.

## §4 fail-closed

`bounded > 0` 이면 계획을 거부한다(`ERRCODE_INSUFFICIENT_PRIVILEGE`).
103개 쿼리 실측에서 이 신호의 정상 쿼리 오탐은 0이었다(`unresolved` 는 2).
중첩 30·60단 우회가 이 경로로 닫힌다.

## §5 구현 중 실제로 겪은 것

**훅 재진입 무한 재귀.** `planner_hook` 안에서 `load_labels()` 가 SPI 로 라벨
쿼리를 돌리는데 **그 쿼리도 `planner_hook` 을 탄다** →
`load_labels → SPI → planner_hook → load_labels → ...` → `stack depth limit
exceeded`. 훅을 다는 확장의 고전적 실수이고 **컴파일이나 정적 분석으로는
안 잡힌다 — 실행해야만 드러난다.** `ipguard_busy` 재진입 가드 + `PG_FINALLY`
로 수정.

**측정 도구의 편향이 또 나왔다.** 집행 채점기가 `__NEST_n__` 생성
플레이스홀더를 펼치지 않아 해당 항목들이 "실행 실패"로 조용히 빠졌다.
`F01`/`F03` 이 누출 목록에 없길래 이상해서 들여다보고 발견했다.
**측정 도구도 대상과 같이 검증해야 한다** — 2라운드의 write 축 누락에 이어
두 번째다.

## §6 아직 안 한 것

1. **성능 미측정.** `planner_hook` 이 계획마다 SPI 로 라벨을 다시 읽는다.
   캐시가 없다. 이 서버는 공유라 성능 측정 자체가 불가하다(README 참조).
2. **서브쿼리 출력이 바깥 술어에 쓰이는 경우** — `SELECT id FROM (SELECT id,
   ssn FROM cust) t WHERE t.ssn = $1` 처럼 마스킹된 컬럼이 바깥 술어에 쓰이면
   결과 행이 줄어든다. 누출이 아니라 **정합성 변경**이다. 코퍼스에 항목이
   없어 측정하지 못했다 — 다음 라운드 필수 항목.
3. **DML/COPY 경로의 집행 미검증.** `write` 축 탐지는 되지만 차단은 미구현.
4. `bounded` 오탐 0은 103개 쿼리 기준이지 운영 오탐률이 아니다.
