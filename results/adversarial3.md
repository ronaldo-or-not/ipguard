# 적대적 시험 3라운드 — 판정식과 센티널 (2026-08-08)

**표적은 가장 젊은 코드다.** 의미 발산 판정식(R1/R2/R3)과 숫자 마스크 센티널
변경은 방금 붙였고, 이전 두 라운드가 **결함 11건을 찾았는데 기본 코퍼스
72항목은 그중 0건을 찾지 못했다.** 새 기능을 붙였으면 새로 쳐야 한다.

**공격 30건, 최종 방어 30건.** 그 과정에서 **결함 4건**을 찾았고 전부 고쳤다.

원시 출력: [`adversarial3.txt`](adversarial3.txt) ·
코퍼스: [`../corpus/adversarial3.json`](../corpus/adversarial3.json)

## ★★ 가장 큰 것 — 중첩 집합연산에서 PII 가 평문으로 나갔다

```sql
SELECT * FROM (SELECT 'zzz'::text AS v UNION ALL SELECT ssn FROM cust WHERE id=1) t
```
```
 zzz
 800102-1000001        ← 평문 주민번호
```

**탐지도 집행도 못 했다** — `ipguard_verdict` 가 `pass / masked=0 / out_pii=(없음)`
을 돌려줬다. 즉 "이 쿼리엔 PII 가 없습니다" 라고 **자신 있게 틀린 답**을 했다.

원인: 최상위 집합연산은 `walk_setop`/`mask_setop` 이 따로 처리하지만,
집합연산이 **서브쿼리나 CTE 안에 있으면** 바깥 `Var` 가 맨 왼쪽 팔의
`TargetEntry` 만 가리킨다. 나머지 팔은 아무도 방문하지 않는다.

**기존 코퍼스가 왜 못 잡았나:** `V04`/`V07` 은 PII 를 **왼쪽 팔에** 뒀다.
그러면 우연히 맞게 동작한다. PII 를 왼쪽이 아닌 팔에만 두는 순간 샌다.
왼쪽/오른쪽 대칭성을 의심해 본 적이 없었던 것이 빈틈이었다.

같은 결함의 세 형태를 회귀 가드로 박았다 — `X26`(2-arm), `X27`(3-arm 가운데),
`X28`(CTE 로 감싼 것).

### 이 결함이 가르쳐 준 구조적 사실

**분석기가 집행기를 게이트한다.** `ipguard_planner` 는 `ctx.out_kinds != NIL`
일 때만 `mask_output` 을 부른다. 그래서 **탐지 미스가 곧 집행 미스**가 된다 --
변이기는 이 경우를 이미 올바르게 처리하고 있었는데도(`mask_setop` 호출이
들어 있었다) 한 번도 불리지 않았다.

집행기를 아무리 튼튼하게 만들어도 분석기가 못 보면 소용이 없다. 두 지표를
따로 재야 하는 이유가 하나 더 늘었다.

## 나머지 결함 3건

| | 공격 | 무엇이 틀렸나 |
|---|---|---|
| `X05`/`X29` | `EXCEPT ALL` | `ALL` 이면 값 비교가 없다고 봤다. **틀렸다** — 다중집합 차집합은 여전히 값을 비교한다. 서로소 집합에서 원본 49행이 마스킹 후 0행이 된다. `ALL` 이 값 비교를 없애는 것은 **`UNION` 뿐**이다 |
| `X06` | `INTERSECT ALL` | 동일 |
| `X07` | `SELECT DISTINCT s FROM (… UNION ALL …) t` | 술어 쪽 `Var` 해석이 집합연산 팔을 안 봤다. 10000행 → 1행 붕괴를 아무도 못 잡았다 |
| `X21` | `count(*) FILTER (WHERE salary IS NOT NULL)` | **변이기가 `FILTER` 안까지 마스킹했다.** `FILTER` 는 술어인데 마스크값과 비교되어 `1000 → 0`. 우리가 마스킹 뷰를 비판한 바로 그 실패를 우리가 하고 있었다 |

`X21` 은 설계 원칙 위반이라 특히 뼈아프다 — *"술어는 건드리지 않는다"* 가
이 프로젝트가 뷰 방식 대비 내세우는 근거인데, `Aggref->aggfilter` 와
`WindowFunc->aggfilter` 가 예외 처리되지 않고 있었다.

## 방어한 것 (설계가 맞게 동작한 축)

- 서수 `GROUP BY 1`, `DISTINCT ON`, `ROLLUP`, `CUBE` — 전부 잡힘
- 집계를 서브쿼리/CTE 안에 숨기기, `HAVING` 에만 두기 — 전부 잡힘
- 순서집합 집계(`percentile_cont`/`mode() WITHIN GROUP`), `corr()` — 전부 잡힘
- `LIMIT` 을 서브쿼리로 밀어넣기, `FETCH FIRST`, `OFFSET` 단독 — 전부 잡힘
- `ntile`, 프레임 지정 누적합 — 전부 잡힘
- **음성 대조군 6건 전부 통과** — 과거부/과마스킹 0

## 라벨을 고친 2건 (숨기지 않는다)

빨간 것을 초록으로 만들려고 기대값을 고치는 것은 이 프로젝트에서 계속
거부해 온 짓이다(`E17`/`E18` 때 `derived_only` 필드를 따로 만든 이유). 이번에
2건을 고쳤고, 이유를 남긴다:

- **`X08`** `HAVING count(DISTINCT ssn) > 1` — `HAVING` 은 술어다. 설계상 술어는
  실값을 본다(문서화된 부채널). 마스킹이 발동하지 않으므로 발산도 없다.
  **내 기대값이 처음부터 틀렸다.**
- **`X21`** — 처음 기대값 `refuse` 는 결함이 있던 상태를 전제로 한 것이었다.
  결함을 고치자 올바른 동작이 "술어이므로 손대지 않음" = `pass` 가 됐다.
  **라벨이 아니라 코드를 고쳐서 정답이 달라진 경우다.**

## 내 측정 스크립트가 또 같은 실수를 했다

우회를 손으로 확인하려고 쓴 임시 SQL 이 `SELECT count(*) FROM (q) z` 형태였다.
그 래퍼는 출력에서 PII 를 참조하지 않으므로 **마스킹이 아예 발동하지 않는다.**
그래서 `EXCEPT ALL` 이 "변화 없음"으로 보였고, 하마터면 결함을 놓칠 뻔했다.
같은 실패 양식이 이걸로 일곱 번째다 — 채점기 본체에는 빌더를 한 곳에 모아
막아 뒀지만, **임시 검증 스크립트에는 그 보호가 없다.**
