# 커버리지 감사 — 막을 수 없으면 감지한다 (2026-08-08)

4라운드가 남긴 가장 큰 미해결 구멍: **파티션 `DETACH` 는 어떤 라벨 키잉으로도
못 막는다.** 상속 연결이 끊기면 자식은 라벨 없는 독립 테이블이 되고,
**데이터는 같은 파일에 그대로 있다.** 월별 파티션을 떼어 아카이브하는 것은
금융권 표준 운영이므로 실전에서 반드시 밟는다.

막을 수 없으면 **감지**해야 한다.

원시 출력: [`coverage.txt`](coverage.txt) ·
도구: [`../tools/score_coverage.py`](../tools/score_coverage.py)

---

## ★ 설계 원칙 — 감사는 집행의 입력이 아니다

`load_labels` 는 **라벨 테이블만** 근거로 삼는다. 컬럼명 휴리스틱을 집행에
넣는 순간 코퍼스 측정이 무의미해지기 때문이다(자기가 만든 규칙으로 자기를
채점하게 된다).

감사기가 내놓는 것은 **사람이 검토할 후보**이고, 사람이 라벨 테이블에 넣어야
비로소 효력이 생긴다. **이 분리를 깨면 안 된다.**

## 두 감사기

| | 무엇을 보는가 | 강점 | 약점 |
|---|---|---|---|
| **구조** `ipguard_coverage()` | 라벨된 컬럼과 **이름+타입**이 같은데 라벨 없음 | 싸다. 데이터를 안 읽는다 | 이름을 바꾸면 못 잡는다 |
| **값** `ipguard_coverage_deep()` | 표본 값이 라벨된 컬럼과 **겹침** | 이름이 달라도 잡는다 | 비싸다. 파생 컬럼은 값이 안 겹쳐 못 잡는다 |

**상호보완이므로 둘 다 돌려야 한다.**

## 결과

현재 스키마에서 라벨 없이 PII 를 들고 있는 것은 3건이다(코퍼스가 물질화
클래스를 보여주려고 일부러 남겨 둔 것들). 둘 다 **전부 찾고 오탐이 없다**:

| | 정탐 | 오탐 | 미탐 |
|---|---:|---:|---:|
| 구조 감사 | **3/3** | **0** | **0** |
| 값 감사 | **3/3** | **0** | **0** |

DDL 시나리오:

| 시나리오 | 구조 | 값 | 실제 평문 누출 |
|---|---|---|---|
| **파티션 `DETACH`** | 잡음 | 잡음 | 예 |
| CTAS 사본 | 잡음 | 잡음 | 예 |
| **이름 바꾼 사본** | **못 잡음** | **잡음** | 예 |
| 음성 대조군 (PII 아닌 사본) | 안 잡음 | 안 잡음 | — |

`DETACH` **전에는 0건**(자식이 상속으로 라벨됨), **후에 즉시 플래그**된다.

## ★ 감사기가 우리 코퍼스에서 진짜 구멍을 찾았다

첫 실행에서 `cust_w` 의 `phone`·`addr`·`birth`·`acct_no` 4개가 나왔다.
확인해 보니 진짜였다:

```sql
SET ipguard.enforce = on;
SELECT phone, addr FROM cust_w LIMIT 1;
   010-1001-0001 | 서울특별시 동작구 흑석로 2길 2      ← 평문
```

`cust_w` 는 `cust` 와 같은 컬럼 구조인데 라벨이 `ci`/`name`/`ssn` 3개만
붙어 있었다. **아무도 몰랐다** — 코퍼스 쿼리 중 `cust_w` 의 그 컬럼들을
조회하는 것이 하나도 없었기 때문이다.

> **쿼리 기반 시험은 쿼리하지 않은 컬럼을 구조적으로 볼 수 없다.**
> 4라운드에 걸쳐 결함 21건을 찾은 적대적 시험도 이건 못 찾았다.
> 카탈로그를 훑는 감사만이 찾을 수 있는 종류다.

라벨 4건을 메웠고 **전 축을 재측정해 변동 0을 확인**했다 — 코퍼스 쿼리가
그 컬럼들을 안 건드리므로 기록된 숫자에 영향이 없다.

## 2라운드 결론을 정정한다

2R 은 이렇게 적었다:

> 순회기로는 **원리적으로 회수 불가한 클래스**를 규명했다 — 구체화 뷰,
> CTAS 사본, 생성 컬럼.

**절반만 맞았다.** 카탈로그 연결이 없다는 것은 사실이고, 그래서 **자동 전파는
불가능**하다. 그러나 **사본 자체에 라벨을 붙이면 마스킹된다:**

```sql
CREATE MATERIALIZED VIEW cov_mv AS SELECT id, ssn FROM cust;
SELECT ssn FROM cov_mv;                        -- 800102-1000001   평문

INSERT INTO pii_label VALUES ('cov_mv','ssn','ssn');
SELECT ssn FROM cov_mv;                        -- **************   마스킹
```

CTAS 사본도 같다. 즉 **막을 수 없는 것은 전파이지 집행이 아니었고, 진짜로
없던 것은 "사본이 생겼다는 사실을 아는 수단"이었다.** 그게 이 감사기다.

같은 정정이 4R Y08(FDW)에도 적용된다 — 외부 테이블도 직접 라벨링하면 된다.

**남는 진짜 한계는 파생 컬럼이다.** `gen_t.ssn6 = substr(ssn,1,6)` 은 값이
겹치지 않아 값 감사도 못 잡고 이름도 다르다. 여기는 여전히 열려 있다.

## 운영 절차

```sql
-- 정기 배치 (구조 감사는 싸므로 자주, 값 감사는 야간에)
SELECT * FROM ipguard_coverage();
SELECT * FROM ipguard_coverage_deep(sample_rows => 500);

-- 라벨 자체의 무결성 (복원 직후 필수)
SELECT * FROM ipguard_verify_labels();
```

셋 다 **빈 결과가 정상**이다. 나온 것은 사람이 보고 라벨 테이블에 넣는다.

## 한계

- 값 감사는 라벨된 컬럼 × 후보 컬럼 곱만큼 표본 질의를 돌린다. **쿼리 경로가
  아니라 정기 배치용**이다.
- 저카디널리티 컬럼(5개 미만 고유값)은 기준으로 쓰지 않는다 — 우연 일치가
  너무 많다.
- 파생 컬럼(`substr`, 해시, 마스킹된 사본)은 두 감사 모두 못 잡는다.
- 감사기가 찾은 것이 **실제로 PII 인지는 사람이 판단한다.** 이름+타입 일치는
  강한 신호지만 증거는 아니다.
