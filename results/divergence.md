# 마스킹 정합성 발산 — 구멍 측정 + 판정식 구현 (2026-08-08)

**질문:** ipguard 는 *"마스킹이 결과를 조용히 바꾸면 거부한다"* 고 주장한다.
실제로는 얼마나 지키는가?

**측정 결과 조용히 틀리는 것이 절반 가까이였고 거부는 0건이었다.** 판정식
(R1~R3)을 구현해 **전부 거부**하도록 만들었고, 그 대가로 **TPC-H 에서 23% 가
거부된다.** 그리고 판정식으로도 못 메우는 자리가 있어 **숫자 마스크 센티널을
0 에서 NULL 로 바꿨다**(아래 마지막 절).

| | 판정식 OFF (기본) | 판정식 ON |
|---|---:|---:|
| 발산 코퍼스에서 조용히 틀림 | **19 / 45** | **0 / 45** |
| 마스킹됐지만 알아볼 수 없음 | 3 | **1** |
| 거부된 쿼리 | 0 | 28 |
| 음성 대조군 오염 | 0 / 4 | **0 / 4** |
| 거래계 코퍼스 카디널리티 왜곡 | 6 | **0** |
| 거래계 코퍼스 과거부 | 0 | **0** |
| **TPC-H 거부율** | **0 / 22** | **5 / 22 (23%)** |
| TPC-H 마스킹 발동 쿼리 대비 | 0 / 7 | **5 / 7 (71%)** |

**이 표가 이 문서의 요점이다.** 조용한 오답을 없애는 값이 분석 워크로드
18% 거부다. 거래계에서는 0% 다 -- 어느 쪽 워크로드냐가 도입 가능 여부를 가른다.

[`tpch-strict.txt`](tpch-strict.txt) ·

## 왜 이걸 쟀나

집행기가 실제로 거부하는 조건은 **하나뿐이다** — 마스킹된 서브쿼리/CTE 출력을
술어가 참조하는 경우. 나머지 발산은 `intrinsic`("마스킹 정의상 불가피")으로
분류해 통과시킨다.

그 분류는 **정책 선택이지 건전성 논증이 아니다.** 심사위원은 여기를 찌른다:

> "DISTINCT 가 10000행을 1행으로 무너뜨리는데 그걸 에러 없이 돌려준다면
> 무엇이 건전한가?"

그래서 답을 미리 숫자로 만들어 뒀다.

## 결과

`agg-num` 은 숫자형 PII(급여·상여) 축이다 — [`../corpus/numeric-schema.sql`](../corpus/numeric-schema.sql).

| class | 무변화 | 마스크값(의도) | **구별 불가** | 카디널리티 붕괴 | **조용한 오답** |
|---|---:|---:|---:|---:|
| dedup (DISTINCT/UNION) | 0 | 0 | 0 | **2** | 0 |
| groupby | 0 | 0 | 0 | **2** | 0 |
| setop (EXCEPT/INTERSECT) | 0 | 0 | 0 | **2** | 0 |
| agg-count | 0 | 0 | 0 | 0 | **3** |
| agg-date | 0 | 1 | 0 | 0 | **3** |
| **agg-num** | 0 | 0 | **4** | **1** | **2** |
| agg-text | 0 | 2 | 0 | 0 | 0 |
| window | 0 | 3 | 0 | 0 | 0 |
| orderby | 1 | 1 | 0 | 0 | 0 |
| join | 1 | 0 | 0 | 0 | 0 |
| control | 4 | 0 | 0 | 0 | 0 |

**음성 대조군 4/4 깨끗** — 측정기가 아무데서나 발산을 만들어내는 게 아니다.

## ★ 가장 위험한 것은 행 수를 안 바꾼다

행 수 기반 탐지기로는 **6건이 안 잡힌다.** 출력이 PII 가 아니라 평범한
숫자라서, 클라이언트는 마스킹이 일어난 사실조차 알 수 없다.

| 쿼리 | 원본 | 마스킹 후 |
|---|---:|---:|
| `SELECT count(DISTINCT ssn) FROM cust` | 10000 | **1** |
| `SELECT count(DISTINCT birth) FROM cust` | 10000 | **1** |
| `SELECT grade, count(DISTINCT ssn) ... GROUP BY grade` | (A, 3333) | **(A, 1)** |
| **`SELECT round(avg(extract(year FROM birth)))`** | **1993** | **1900** |

마지막 줄이 최악이다. `**********` 같은 마스크 표식이 아니라 **1900 이라는
그럴듯한 연도**가 나온다. "우리 고객 평균 출생연도 1900년"은 눈에 띄지만,
같은 집계를 부분집합에 걸면 눈에 안 띄는 값이 얼마든지 나온다.

`SELECT ssn, count(*) FROM cust GROUP BY ssn HAVING count(*) > 1` 은 방향까지
뒤집는다 — 원본 **0행**(중복 없음)이 마스킹 후 **1행**(중복 있음)이 된다.

## ★★ 숫자형에서 R2 의 면제 근거가 깨졌다

값 보존 집계(`max`/`min`)를 면제한 근거는 **"결과가 마스크값이므로 클라이언트가
알아본다"** 였다. 숫자형 PII 를 넣고 재 보니 그 전제가 성립하지 않는다:

| 마스크 센티널 | 알아볼 수 있나 |
|---|---|
| `'**************'` (text) | 명백하다 |
| `1900-01-01` (date) | 의심스럽다 |
| **`0`** (numeric/int) | **유효한 급여·잔액이다. 구별 불가.** |

```
SELECT max(salary), min(salary) FROM payroll
   원본  69800000.00 / 32000000.00   →   마스킹 후  0 / 0
```

**"최고 급여 0원"은 그럴듯한 답이다.** 별표 하나 없이 나가고, 클라이언트는
마스킹이 일어났다는 사실조차 모른다. 텍스트에서는 안 보이던 구멍이다.

그래서 R2 를 고쳤다 — **마스크 센티널이 정상 값과 구별되지 않는 타입
(int2/4/8, float4/8, numeric)이면 값 보존 집계여도 면제하지 않는다.**
`max(ssn)` 은 여전히 통과하고 `max(salary)` 는 거부된다.

**이 수정의 과거부 비용은 0이었다** — TPC-H 거부는 4/22 그대로다.

> 이 자리에서 별개 질문이 나왔다 — **센티널이 0 인 것 자체가 옳은가.**
> 재서 정했다. 맨 아래 절 참조.

## 측정 중에 뒤집힌 예측 하나

`SELECT count(*) FROM cust a JOIN cust b ON a.ssn = b.ssn` 는 교차곱이 될
것으로 예상했는데 **아무것도 안 바뀐다.** `ssn` 이 조인 술어에만 있고 출력이
아니라 마스킹되지 않기 때문이다. 술어 불가침 설계가 의도대로 동작한다는
증거이고, 예측이 아니라 측정을 믿어야 하는 이유이기도 하다.

## 판정식 (구현 완료, 기본 비활성)

처음에는 "출력 타입이 PII 타입과 다르면 조용한 오답"이라는 규칙을 세웠는데
**틀렸다** -- `sum(숫자 PII)` 는 타입이 같은데도 조용히 0 이 된다. 측정이
가리킨 실제 구분선은 타입이 아니라 **행 단위 파생이냐 행 간 연산이냐** 였다:

- `substr(ssn,1,6)` → `"******"` — 행 단위. 클라이언트가 `f(마스크)` 를 받는다.
  그게 마스킹의 정의다. **허용.**
- `count(DISTINCT ssn)` → `1` — 행 간. 답이 값이 아니라 **모집단에 대한 통계**
  인데 마스킹이 모집단을 파괴했고, 출력은 평범한 숫자다. **거부.**

두 규칙으로 좁혔다:

| | 조건 | 근거 |
|---|---|---|
| **R1** 카디널리티 | 마스킹된 값이 `DISTINCT`/`GROUP BY` 키이거나 비-`ALL` 집합연산의 출력 | 결과 행 수가 마스크값에 좌우된다 |
| **R2** 통계 | 마스킹된 값이 **값 보존이 아닌** 집계의 인자 | 마스크값에서 평범한 숫자가 만들어진다 |
| **R3a** 윈도우 | 마스킹된 값이 윈도우의 `PARTITION BY`/`ORDER BY` 키 | 순위·행번호가 마스크 순서에서 나오는데, 그 컬럼엔 마스킹 표시가 없다 |
| **R3b** 행 선택 | 마스킹된 값이 정렬 키이고 `LIMIT`/`OFFSET` 이 있다 | **어느 행이 나올지**가 마스크값에 좌우된다 |

값 보존 집계(`max`/`min`/`string_agg`/`array_agg`/`json_agg`…)는 결과가 입력
값들 중 하나이거나 그 연결이라, 전부 마스크값이면 결과도 마스크값이다 --
클라이언트가 알아본다. `DISTINCT` 집계는 값 보존이어도 고유값 수에 의존하므로
거부한다.

**Var 해석이 필요하다.** 한 겹만 감싸도 키가 그냥 `Var` 가 되어 뚫린다:

```sql
SELECT t.ssn FROM (SELECT ssn FROM cust) t GROUP BY t.ssn
```

바깥 `GROUP BY` 키는 `Var` 이고 `mask()` 는 서브쿼리 안에 있다. 첫 구현이
이걸 놓쳐 `A07` 한 건이 계속 왜곡됐고, 술어 충돌 감지기의 Var 해석을
재사용해 메웠다. 같은 수정으로 TPC-H `Q22`(`substring(c_phone…)` 그룹핑)도
잡혔다 -- 과거부가 3 → 4 로 **늘었다.** 정확해질수록 비용이 오른다.

**기본은 `allow` 다.** `ipguard.on_divergence = error|warn|allow` 로 켠다.
켜면 정상 분석 쿼리가 막히므로 운영 도입은 워크로드 성격에 달렸다.

## 선행연구와의 위치

이 발산은 업계가 다 아는 것이다 — SQL Server / Snowflake / Databricks 문서가
"동적 데이터 마스킹은 추론을 막지 못한다"고 명시한다. 그런데 **결정 가능한
건전성 조건으로 형식화한 문헌은 못 찾았다.**

- **Blockaid** (OSDI 2022): 허용된 뷰로 답할 수 **없으면** 거부
- **Mascara** (SIGMOD 2025): 손실이 가장 적은 준수 재작성으로 **열화**
- **아무도** 의미 발산을 이유로 거부하지 않는다

## R3 — 윈도우와 행 선택 (나중에 추가)

처음에는 이 둘을 "출력이 전부 마스킹되니 클라이언트가 어차피 구분 못 한다"는
이유로 뺐다. **틀렸다.** 마스킹된 컬럼과 평범한 컬럼은 같은 행에 **함께**
나가고, 평범한 쪽에는 마스킹 표시가 없다:

```
SELECT id, ssn, dense_rank() OVER (ORDER BY ssn) AS r FROM cust WHERE id < 6
   r:  1,2,3,4,5   →   전부 1        (ssn 은 ****, r 은 평범한 정수)

SELECT id, ssn FROM cust ORDER BY ssn LIMIT 5
   id: 100,200,300,400,500  →  1,2,3,4,5     (완전히 다른 5행)
```

`LIMIT` 유무가 갈림선이다. 없으면 행 **순서**만 바뀌고 집합은 그대로다
(`DV39` 는 통과). 붙는 순간 **어느 행이 나올지**가 마스크값에 좌우된다.

**측정기도 같이 고쳐야 했다.** 대표행 하나만 보던 판정이 이 클래스를 통째로
놓쳤다 -- `dense_rank` 가 1,2,3,4,5 → 전부 1 인데 첫 행은 양쪽 다 1 이라
"변화 없음"으로 찍혔다. 그리고 행을 한 덩어리로 비교하니 음성 대조군
(`ORDER BY id LIMIT 5`)까지 "조용한 오답"이 됐다 -- 같은 행에 마스킹된 `ssn`
이 있다는 이유만으로. 이제 앞 20행을 짝지어 **필드별로** 비교하고, 마스크로
바뀐 필드는 빼고 평범한 필드가 바뀌었는지만 본다.

**이 규칙의 비용은 TPC-H 에서 +1 이다** (4/22 → 5/22). 다만 그걸 재려고
**코퍼스에 빠져 있던 `LIMIT` 절을 명세대로 채워야 했다** -- Q2/Q3/Q10/Q18/Q21
에 `first 100/10/20/100/100` 이 없어서 R3b 가 워크로드에서 아예 검증되지
않고 있었다. 채우니 Q2 가 걸렸다.

## 아직 못 덮는 것
- **`ORDER BY` 만 있고 `LIMIT` 이 없는 경우** — 행 집합은 그대로고 순서만
  바뀐다. 클라이언트가 다시 정렬할 수 있으므로 뺐다(`DV39`).
- **`lag`/`lead` 의 일부 경우** — `DV35` 는 표본 20행 안에서 값이 안 바뀌어
  판정기가 "의도한 동작"으로 봤다. R3a 가 규칙으로는 잡지만 **측정으로는
  확인하지 못한 것**이므로 적어 둔다.

## 한계

- 24건은 손으로 고른 것이다. 실제 워크로드 분포가 아니다.
- 크기는 이 데이터(10000행, ssn 전부 고유)에 의존한다. 중복이 많은 컬럼이면
  붕괴 배율이 작아진다.
- `orderby`/`window` 를 "의도한 동작"으로 센 것은 출력이 전부 마스킹돼

- 숫자형 PII 는 `h5.payroll`(급여·상여 1000행)로 실측했다. `h5.cust` 에

  참조 항목의 마스킹 컬럼 수가 바뀌어 이미 기록된 모든 숫자가 흔들리기
  때문이다. 실제로 추가 후 전 축을 재측정해 변동 0을 확인했다.

## 마스크 센티널: `0` vs `NULL` — 재서 정했다

**결론: 기본값을 `nullify` 로 바꿨다.** `ipguard.numeric_mask = zero` 로 되돌린다.

판정식(R1~R3)은 **행 간 연산**만 잡는다. 그래서 가장 흔한 쿼리 모양이 그대로
남는다:

```sql
SELECT id, salary FROM payroll        -- 집계도 그룹핑도 정렬도 없다
```

어느 규칙에도 안 걸리는데 `salary` 자리에 **`0` 이 나간다.** 텍스트라면
`**********` 이라 한눈에 보이지만, 0 은 유효한 급여다. 판정식으로 메울 수 없는
자리이므로 **센티널 자체를 바꾸는 것 말고는 방법이 없다.**

실측 (45건, 판정식 ON):

| | 알아볼 수 없음 | 거부 | TPC-H 과거부 |
|---|---:|---:|---:|
| `zero` | **3** | 30 | 5/22 |
| **`nullify`** | **1** | **28** | 5/22 |

`nullify` 가 모든 축에서 같거나 낫다. 거부가 2건 적은 것은 `max(salary)`/
`min(salary)` 가 `NULL` 을 돌려주어 **알아볼 수 있게 되므로** 값 보존 집계
면제를 되살릴 수 있기 때문이다 — R2 의 숫자 예외가 필요 없어진다.

### 대가 두 가지 (숨기지 않는다)

**1. `count(col)` 이 조용히 틀린다.** `0` 은 NULL 이 아니므로 `count(salary)`
가 정확히 1000 이었는데, `NULL` 로 바꾸면 **0** 이 된다. 다만 `count` 는 값
보존 집계가 아니므로 **R2 가 잡는다** — 판정식을 켜면 거부된다.

**2. `coalesce(salary, 0)` 한 줄로 무력화된다.**

```
   원본 37400000.00  →  NULL 마스크  →  coalesce(…, 0)  →  0
```

방어적으로 `coalesce` 를 쓰는 애플리케이션 코드에서는 `NULL` 의 "알아볼 수
있음"이 사라진다. **단 이건 `zero` 대비 퇴행이 아니다** — `zero` 에서도 같은
0 이 나간다. `nullify` 의 이점이 그 경로에서만 없어질 뿐이다. 판정식 ON 에서
남는 1건이 정확히 이것이다.

### 측정하지 못한 축

**`NOT NULL` 을 기대하는 클라이언트가 깨진다.** 엄격한 ORM 매퍼는 `NULL` 에서
예외를 던진다. 이건 DB 안에서 잴 수 없는 축이고, 실제 도입 시 가장 먼저 부딪힐
문제다. 그래서 스위치를 남겼다.

### 함정 하나 (옵션 이름)

값을 `null` 이라 부르면 안 된다. `SET ipguard.numeric_mask = null` 은 SQL
예약어라 문자열이 아니라 NULL 로 해석돼 **조용히 기본값이 된다.** 처음에
그렇게 만들었다가 두 설정의 측정값이 똑같이 나와서 발견했다. 이름을
`nullify` 로 바꿔 함정을 없앴다.
