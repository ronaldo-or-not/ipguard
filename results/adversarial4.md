# 적대적 시험 4라운드 — 카탈로그 / DDL 표면 (2026-08-08)

1~3라운드는 전부 **SQL 문장**을 쳤다. 이번 표적은 **라벨이 카탈로그에 매달리는
방식**이다.

```sql
JOIN pg_class c ON c.relname = l.relname            -- 이름으로 붙는다
               AND c.relnamespace = 'h5'::regnamespace
... UNION ALL pg_inherits 로 자손 전개 ...            -- 상속으로 전파된다
JOIN pg_attribute a ON a.attname = d.attname        -- 컬럼도 이름으로
```

**시나리오 10건 중 6건에서 평문 주민번호가 나왔다.** 단일 라운드 최대 수확이다.
그중 1건을 고쳤고, 1건은 재분류했고, 4건은 **설계 결정이 필요한 것**으로 남겼다.

원시 출력: [`adversarial4.txt`](adversarial4.txt) ·
도구: [`../tools/score_adversarial4.py`](../tools/score_adversarial4.py)

## ★ 고친 것 — 라벨을 붙여도 즉시 효력이 없었다 (Y07)

```
PREPARE p AS SELECT ssn FROM t;  EXECUTE p × 6      -- generic plan 캐시됨
INSERT INTO pii_label VALUES ('t','ssn','ssn');     -- 컬럼을 라벨링
EXECUTE p                                           -- 800102-1000001  ← 평문
```

새 세션에서는 정상 마스킹된다. 즉 순수한 **계획 캐시 staleness** 인데,
**커넥션 풀 환경에서 가장 위험한 형태다.** 풀의 세션은 몇 시간에서 며칠씩
살아 있으므로 "컬럼을 라벨링했다"가 언제 효력을 갖는지 알 수 없고, 에러도
경고도 없이 계속 샌다. 보안 담당자는 라벨을 넣고 조치 완료로 기록한다.

**고쳤다.** 라벨 테이블에 문장 트리거를 달아 relcache 무효화를 방송하고,
각 백엔드가 그 신호를 받아 `ResetPlanCache()` 를 부른다 — PostgreSQL 이
카탈로그 변경을 전파하는 표준 경로다.

```sql
SELECT ipguard_watch_labels('h5.pii_label');   -- 한 번만
```

라벨 테이블은 확장 소유가 아니라 사용자 스키마에 있으므로 트리거는 명시적으로
걸어야 한다. **이 한 줄을 빠뜨리면 위 누출이 그대로 살아 있다** — 설치 문서에
반드시 들어가야 하는 항목이다.

## ★ 설계 결정이 필요한 것 — 라벨이 이름에 매달려 있다 (Y01~Y03)

```sql
ALTER TABLE h5.cust RENAME TO cust_v2;          -- 라벨 전멸
ALTER TABLE h5.cust RENAME COLUMN ssn TO rrn;   -- 그 컬럼 라벨 전멸
ALTER TABLE h5.cust SET SCHEMA archive;         -- 라벨 전멸
```

전부 **DDL 한 줄로 마스킹이 꺼진다.** 에러도 경고도 없다. 마이그레이션 스크립트
한 줄이 보안 컨트롤을 끄는 셈이고, 아무도 모른다.

**고치는 방법은 명확하지만 값이 있다:**

| 방법 | 장점 | 대가 |
|---|---|---|
| 라벨을 **OID**(`attrelid`,`attnum`)로 키잉 | RENAME·SET SCHEMA 전부 면역 | 사람이 못 읽는다. 덤프/복원에서 OID 가 바뀐다. **기록된 모든 측정값이 흔들린다** |
| DDL **이벤트 트리거**로 라벨 자동 갱신 | 이름 키잉 유지 | 이벤트 트리거는 superuser 권한 필요. RENAME 의 old/new 추출이 번거롭다 |
| 라벨 없는 릴레이션 **접근 자체를 거부** | 확실 | 라벨 없는 테이블이 대부분인 실제 DB 에서 못 쓴다 |

**이번 라운드에서 고르지 않았다.** 라벨 키잉 방식은 스키마·코퍼스·기록된
숫자 전체에 영향을 주는 결정이라, 발견을 정확히 기록하고 별도로 결정한다.
지금 급히 바꾸면 이 프로젝트에서 가장 값진 자산(재현 가능한 측정 이력)이
무너진다.

## 알려진 클래스로 확인된 것 (Y04)

파티션을 `DETACH` 하면 자식은 독립 테이블이 되고 `pg_inherits` 연결이 끊겨
라벨을 잃는다. **2라운드가 규명한 "라벨 없는 릴레이션으로 물질화되면 회수
불가" 클래스와 같다** (구체화 뷰, CTAS 사본, 생성 컬럼).

다만 `DETACH` 는 그 클래스 중에서도 특히 나쁘다 — 데이터를 복사하지 않고
**같은 파일을 그대로 두고 라벨만 잃는다.** 파티션 순환(월별 파티션 detach 후
아카이브)은 금융권 표준 운영이므로 실전에서 반드시 밟는다.

`ATTACH`(Y05)와 `INHERITS`(Y06)는 정상 동작 — 전파 자체는 살아 있다.

## 재분류 — FDW 는 메커니즘 실패가 아니다 (Y08 → Y10)

외부 테이블에 **직접 라벨을 붙이면 마스킹된다**(Y10 양성 대조군으로 확인).
원격 원본 테이블의 라벨이 전파되지 않을 뿐이다 — 애초에 전파될 경로가 없다
(다른 DB 의 카탈로그다).

즉 "외부 테이블도 라벨링해야 한다"는 **운영 수칙**이지 메커니즘 결함이 아니다.
다만 조용히 새는 것은 같으므로 커버리지 점검 항목에 들어가야 한다.
