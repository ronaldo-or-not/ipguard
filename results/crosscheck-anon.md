# 독립 구현 교차검증 — 우리 버그인가, 이 부류의 성질인가 (2026-08-08)

3~5라운드가 결함 25건을 찾았다. 그런데 심사위원의 첫 질문은 이것이다:

> *"GUC 를 `PGC_USERSET` 으로 만든 건 당신 실수 아닌가? 라벨을 이름으로 조인한
> 것도. 이게 왜 논문인가?"*

이 반박을 못 막으면 **5라운드 전체가 내 디버깅 기록**이다.

그래서 같은 공격을 **독립된 서드파티 구현**에 걸었다 —
[PostgreSQL Anonymizer](https://gitlab.com/dalibo/postgresql_anonymizer) 1.3.2,
오픈소스 PostgreSQL 마스킹의 사실상 표준.

원시 출력: [`crosscheck-anon.txt`](crosscheck-anon.txt) ·
도구: [`../tools/crosscheck-anon.sh`](../tools/crosscheck-anon.sh)

---

## 결론

| 실패 클래스 | 우리 | anon | 판정 |
|---|---|---|---|
| 우회 (search_path / 스키마 수식) | 뷰 베이스라인 3/3 | **재현** | 부류의 성질 (REVOKE 로만 막힘) |
| **★ 의미 발산 (집계·정렬)** | 45건 중 19건 | **재현, 하드닝 후에도** | **부류의 성질, 문서에 없음** |
| 물질화 사본 (CTAS·MV) | 2R GAP | **재현 (평문)** | 부류의 성질 |
| 스키마 `RENAME` | 4R 에서 뚫림 → OID 로 수정 | **처음부터 안 뚫림** | **우리가 틀렸다** |

## ★★ 핵심 — 하드닝 후에도 남는 것

anon 문서가 권장하는 대로 원본 스키마 접근을 회수(`REVOKE`)해 **우회를 전부
막은 상태**에서 측정했다. 그래도 이렇게 나온다:

| | 원본 | anon 마스킹 롤 |
|---|---:|---:|
| `count(DISTINCT ssn)` | 200 | **1** |
| `SELECT DISTINCT ssn` 행 수 | 200 | **1** |
| `ORDER BY ssn LIMIT 5` 의 id | `28,56,84,112,140` | **`1,2,3,4,5`** |
| `max(ssn)` | `800128-1000195` | `**************` (알아볼 수 있음) |

**에러도 경고도 없다.** 그리고 anon 문서 전체를 훑어도 이 클래스에 대한 언급이
없다 — `aggregate`/`distinct`/`inference` 검색 결과는 전부 *generalization*
기능이 "통계에 유용하다"는 반대 방향의 서술이다.

즉 **의미 발산은 우리 구현의 버그가 아니다.** 업계 표준 오픈소스 마스킹 확장이,
자기 문서대로 하드닝한 상태에서, 정확히 같은 방식으로 조용히 틀린다.

## 우회 — 같은 메커니즘, 같은 결과, 같은 비용

anon 의 동적 마스킹은 **롤의 `search_path` 를 조작**한다. anon 문서의 표현:

> *"This is because the `search_path` of the masked role is **rigged**."*

`pg_roles.rolconfig` 를 보면 `{"search_path=mask, public"}` 이 전부다.
그래서 마스킹 대상 롤이 스스로 `SET search_path = public` 하면 평문이 나온다.
스키마 수식(`public.cust`)도 마찬가지다.

이건 우리가 [`view-baseline.md`](view-baseline.md) 에서 마스킹 뷰에 대해 적은
것과 **같은 메커니즘, 같은 우회 3/3, 같은 해법(REVOKE), 같은 도입 비용**이다.
anon 도 튜토리얼 마지막에 `REVOKE ALL ON SCHEMA public FROM jack` 을 한다.

> 그래서 우리 뷰 베이스라인은 인위적으로 만든 허수아비가 아니었다 —
> **현장 표준 구현이 실제로 그 구조다.**

## 우리가 틀렸던 축 — 그래서 이 비교가 믿을 만하다

`ALTER TABLE RENAME` 후에도 anon 의 마스킹은 **살아남는다.**
`SECURITY LABEL` 이 `pg_seclabel` 에 **OID 로** 저장되기 때문이다.

우리는 4R 에서 이걸로 뚫렸고(Y01~Y03), 그 뒤에야 OID 키잉으로 바꿨다.
**anon 이 처음부터 맞았고 우리가 틀렸다.**

이 비대칭이 중요하다. 모든 축에서 우리가 이겼다면 시험 설계를 의심해야 한다.
한 축에서 명확히 졌다는 사실이 나머지 결과를 믿을 만하게 만든다.

다만 anon 은 그 대가로 **`RENAME COLUMN` 이 아예 막힌다** — 마스킹 뷰가 컬럼에
의존하기 때문이다. 뷰 방식은 보안을 지키는 대신 정상적인 스키마 진화를 막는다.
계획 재작성 방식(우리)은 둘 다 통과시킨다.

## 이 결과가 노벨티에 대해 말하는 것

- **마스킹 자체**: 새롭지 않다. anon 이 이미 한다.
- **우회·물질화**: 새롭지 않다. 알려진 운영 문제이고 anon 도 같다.
- **`RENAME` 내성**: 새롭지 않다. anon 이 먼저 맞았다.
- **★ 의미 발산을 결정 가능한 거부 조건으로 형식화**: 재현된 실패이면서
  **어느 구현도, 어느 문서도 다루지 않는다.** Blockaid 는 다른 조건으로
  거부하고, Mascara 는 거부 대신 열화한다. 여기가 비어 있다.

## 한계

- anon **1.3.2**(마지막 PGXS 기반)로 쟀다. 3.x 는 Rust/pgrx 로 재작성됐고 이
  호스트에 Rust 가 없다. 3.x 에서 발산이 다뤄졌을 가능성은 배제하지 못한다 --
  다만 3.x 문서에서도 해당 클래스 언급은 확인하지 못했다.
- 상용 구현(Oracle Data Redaction, SQL Server DDM, Snowflake)은 이 호스트에서
  실행할 수 없다. 벤더 문서가 "DDM 은 추론을 막지 못한다"고 명시하는 것은
  확인했으나, **집계 정합성 파괴를 명시한 문서는 못 찾았다.**
- 데이터는 200행이다. 붕괴 배율은 데이터 분포에 의존한다.
